# Аудит гибрида и всех фичей — 23 октября 2026

Анализ выполнен по `practices_doc.md`, коду генератора, большим и малым
абляциям Mistral, сохранённым полным прогонам GPT-5.4 mini и полным ответам
из `raw_responses.jsonl`. Новые запросы к LLM и БД не выполнялись. Поведение
генератора и существующие результаты не изменялись.

Отдельный GPT-контроль с ambiguity-промптом из `main`: Ambrosia 106/227 =
46,70%. Он не является основным baseline и не участвует в оценке эффекта

Исторический best hybrid хранится в `ablation_results_small/feat_best_hybrid_large`,
несмотря на имя родительской папки. Это большие наборы. На настоящих small
исторические лучшие результаты — 12/22 BIRD = 54,55% и 23/24 Ambrosia = 95,83%.
Эти проценты нельзя переносить на большие наборы.

Ambrosia large исходно содержит 240 вопросов. Три пустые серверные базы
исключают 13 вопросов, и исторический best hybrid, baseline Mistral и новые
сопоставляемые запуски GPT используют одинаковые 227 ID. Историческая абляция
FEAT_6 является исключением: она сохранила 240 ответов, включая ответы без
доступной схемы. В приложенной таблице её качество пересчитано на общих 227 ID.

BIRD здесь — локальный EX-подобный оценщик после преобразования SQLite SQL
в PostgreSQL, а не подтверждённый запуск официального BIRD evaluator. В коде
результаты сравниваются как множества строк: порядок и дубликаты игнорируются.
Исторический best hybrid переоценивался после исправлений оценщика; одиночные
старые абляции не следует автоматически считать заново проверенными тем же
кодом. Их ранжирование — материал для гипотез, не окончательная причинная оценка.

### Ambrosia: что скрывается за Accuracy

| Конфигурация | TP / 67 | FP / 160 | Precision | Recall | F1 | Balanced accuracy |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Mistral baseline | 24 | 57 | 29,63% | 35,82% | 32,43% | 50,10% |
| Mistral best hybrid | 42 | 11 | 79,25% | 62,69% | 70,00% | 77,91% |
| GPT baseline | 0 | 0 | Не определён | 0% | 0% | 50% |
| GPT hybrid | 42 | 36 | 53,85% | 62,69% | 57,93% | 70,09% |

Одинаковое количество TP не означает одинаковые ID. GPT baseline достигает
70,48% предсказанием «всегда однозначно». Новый гибрид увеличивает Accuracy
только на 2,64 п.п., но действительно начинает определять неоднозначность.
Основное отставание от Mistral best hybrid — лишние 25 ложных срабатываний.

### Почему различаются результаты

Подтверждено: одинаковые флаги на разных моделях дали разную частоту
неоднозначности: BIRD 3 у исторического гибрида против 50 у GPT-гибрида.
Отключение FEAT_32/33 при прочих прежних настройках подняло GPT с 38,59% до
46,89%. Это лучшее прямое свидетельство вреда жёсткого ambiguity-gating
для текущего BIRD/GPT. На Ambrosia этот же механизм полезен.

Вероятные факторы: чувствительность модели к формулировкам, перенос настроек,
отобранных на Mistral и маленькой выборке, взаимодействия фичей, различия
выходных лимитов и provider routing. Полной фиксации исходных запросов и
снимков модели в старых экспериментах нет, поэтому один фактор нельзя объявить
единственной причиной. Даже при temperature=0 повторный запуск не гарантирует
те же SQL. Старые абляции логирования тоже отличаются от baseline на несколько
вопросов, что запрещает трактовать любой небольшой прирост как пользу фичи.

## 4. Где прямо сейчас тратятся токены

Полный BIRD без taxonomy сделал 634 успешных вызова:

| Стадия | Вызовов | Входных токенов | Выходных токенов |
| --- | ---: | ---: | ---: |
| Классическая проверка неоднозначности | 241 | 819 821 | 1 241 |
| Декомпозиция №30 | 152 | 82 198 | 25 475 |
| Генерация SQL | 241 | 931 641 | 27 577 |

То есть отключение FEAT_32/33 НЕ отключило классическую проверку. Все её
решения в полном BIRD были OK; на неё ушло 44,7% входных токенов. Для отдельного
режима генерации SQL без отказа можно явно пропускать checker. Это ожидаемая
экономия по наблюдённой трассе, а не уже измеренная новая конфигурация.

На Ambrosia: 139 taxonomy-вызовов (остальные пропустил stop-filter), 78
clarification, 26 decomposition и 149 SQL-generations. Генерация SQL для
однозначных вопросов нужна при оценке SQL, но текущая Ambrosia-метрика оценивает
только неоднозначность. Отдельный detection-only benchmark может её не выполнять;
такой режим нужно явно обозначать, не смешивая его стоимость с end-to-end SQL.

## 5. Проверки и исправления до новых дорогих прогонов

1. Разделить режимы задач: SQL generation и ambiguity detection. Номер
   бенчмарка не должен подменять понимание типа пользовательской задачи.
2. Сохранить проверенные опорные результаты. Добавить режимы skip-classic-check
   для BIRD и без №33 при №34=false для batch Ambrosia; подтвердить smoke-тестом.
3. Для BIRD проверить №15/16 + №17/27 с ограниченным PostgreSQL EXPLAIN
   (без ANALYZE и без эталонного SQL в feedback). Ошибки синтаксиса, имён и типов
   становятся наблюдаемым сигналом исправления. В последнем отчёте 19 DB-ошибок;
   по all_gold_results эталон успел выполниться для всех 19, то есть ошибка была
   на предсказанном SQL. У baseline три из этих вопросов были правильными.
4. Затем отдельные leave-one-out проверки внутри текущего гибрида: №30;
   компактный формат №7 при №2; строгие правила №14 с учётом №29. Не менять
   одновременно много механизмов, иначе источник эффекта снова неизвестен.
5. На Ambrosia разобрать 36 FP по типам. Проверять A1 отдельно от A3a/A3b,
   требовать две конкретные различающиеся интерпретации и конкретные поля.
   Сравнивать precision/recall/F1, а не только Accuracy. Проверять на отдельной
   группе БД/семейств перефразировок, а не подбирать по тем же 227 вопросам.

## 6. Данные для классификатора: что нужно поправить

`build_feature_dataset.py` сохраняет `feature_scores=score`: это правильность
в одиночном запуске, не маргинальная польза фичи. Для анализа полезны отдельно
baseline_correct, feature_correct и utility = feature_correct - baseline_correct
(−1/0/+1). Для выученного предсказания успеха абсолютный score тоже допустим,
но его нельзя называть причинной атрибуцией пользы.

Текущие проблемы данных:

- Нет валидации зависимостей: №3/4/7 запускались без №2; №33 без №32;
  №36 без №15. Их результаты не измеряют заявленный механизм.
- Есть 241 строка large BIRD с 33 scores, но best_combo_correct=false у всех:
  builder ищет устаревшую `feat_4_both`, а не реальный best hybrid.
- Есть 240 строк large Ambrosia: 227 имеют 33 scores, 13 имеют только score
  FEAT_6. Пропущенные наблюдения нельзя считать отрицательными метками.
- В отчёте builder «unsolvable» считается по отсутствующему best_combo, что
  не доказывает неразрешимость вопроса.
- bird_small — подмножество bird_large, ambrosia_small — подмножество large:
  добавлять их как независимые новые примеры нельзя.
- Не хватает model/configuration/schema/prompt/evaluator provenance. Метки
  Mistral нельзя считать готовой разметкой оптимальных фичей GPT.
- Случайный split по вопросам может смешивать одну БД и близкие перефразировки
  между train/test; использовать группы по БД и семействам вопросов. Gold
  difficulty не следует считать доступным production-признаком.
- Глобальные FEAT_N читаются при импорте. Для per-question selector нужны
  instance/configuration-параметры; изменение os.environ внутри query не
  переключает уже импортированные значения и небезопасно при параллельных query.

## 7. Практический порядок следующей работы

Сначала нормализовать результаты и зависимости, исправить лишние стадии и
подключить проверяемый feedback PostgreSQL. Затем получить короткие групповые
абляции на development-наборе. После этого — rule-based selector / простой
