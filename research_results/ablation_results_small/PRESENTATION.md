# Text2SQL: Ablation Study & Feature Engineering
## BIRD + Ambrosia Benchmark Results

---

## Slide 1 — Цель и стартовая точка

**Задача:** построить Text2SQL пайплайн, который одновременно решает две задачи:
- **BIRD** — генерация корректного SQL-запроса по вопросу на естественном языке
- **Ambrosia** — детекция неоднозначных вопросов (вернуть `{"status": "ambiguous"}` вместо SQL)

| Метрика | Baseline | Цель | Достигнуто |
|---------|---------|------|-----------|
| **BIRD** | 36.36% | ≥ 50% | **54.55%** |
| **Ambrosia** | 54.17% | ≥ 70% | **91–96%** |

Baseline = все флаги отключены (чистый пайплайн: вопрос → LLM → SQL).

---

## Slide 2 — Методология: Ablation v2 (leave-one-in)

**Принцип:** baseline = все флаги выключены (чистый пайплайн, 36.36% BIRD / 54.17% AMB). Каждая фича тестируется **в isolation** — только она одна включена, всё остальное выключено. Измеряем Δ относительно этого чистого baseline.

**Датасеты:**
- BIRD small: 22 вопроса, 7 БД → 1 вопрос = 4.55% (высокий шум)
- Ambrosia small: 24 вопроса, 9 БД

**Важное: v1 vs v2.** Первоначальная методология (v1) фиксировала base stack (FEAT_5+12+18+19) и давала недостоверные результаты — без FEAT_12 ambiguity-фильтр помечал 60–80% вопросов как ambiguous, без FEAT_18/19 rate-limit cascade убивал прогон. В v2 каждая фича тестируется от нуля, в полной изоляции.

**Почему не fold-out:** у нас ≤ 24 вопросов на датасет — leave-one-out даёт оценку с высокой дисперсией. Leave-one-in честнее: видно, добавляет ли фича что-то поверх стабильного baseline.

## Slide 4 — Почему FEAT_2 дала самый большой прирост

**FEAT_2 = column statistics (min/max/top-K distinct values, cardinality)**

```
Без FEAT_2:  LLM видит только название колонки "date" типа TEXT
С FEAT_2:    LLM видит: min="199801", max="201212", sample=["200301","199901"]
```

**Три класса ошибок, которые FEAT_2 устраняет:**

1. **Неправильный формат дат.** Когда `yearmonth.Date` = `"YYYYMM"` (не ISO), LLM без статистики генерирует `WHERE date = '2012-01'` → пустой результат. Со статистикой — `WHERE date = '201201'`.

2. **Лишние CAST.** Зная, что min=0, max=1000 — LLM не оборачивает в `TO_DATE()` числовую колонку.

3. **Подбор порогов и агрегаций.** Зная, что `AvgScrMath` лежит в [300, 800] — LLM правильно выбирает `WHERE AvgScrMath > 560` без промахов в масштабе.

**Почему FEAT_3/4 дали меньше (+4.55% vs +9.09%):**
- FEAT_3 (regex-типизация) применима только к TEXT-колонкам, которых в BIRD-схемах меньшинство
- FEAT_4 (row count) полезен для LIMIT-решений, но таких вопросов в small всего 1–2
- Они частично чинят **те же вопросы**, что и FEAT_2 — не-аддитивность сигналов

## Slide 5 — Почему FEAT_1 (FK/PK) вредит BIRD (−9.09%)

**Ожидаемый эффект:** LLM знает, как делать JOIN-ы без угадывания → меньше ошибок JOIN.

**Реальный эффект:** +300–500 токенов в системном промпте на каждую БД.

**Механизм вреда — промпт-перегрузка:**
- В BIRD-датасете БД имеют 3–10 таблиц и 10–30 FK — добавление полного FK-списка удваивает размер промпта
- LLM начинает "следовать" FK даже когда задача не требует JOIN — генерирует лишние JOIN-ы
- На AMB (Ambrosia) FK дают слабый +4.16% — там схемы проще (2–5 таблиц) и лишние токены менее вредны

**Вывод из AutoMeta:** «25%+ of equality join constraints are not documented in FK» — проблема не в отсутствии FK в промпте, а в том, что реальные join-пути вообще могут быть не задокументированы.

## Slide 6 — Структурная проблема: FEAT_32/33 в isolation дают −8%

**FEAT_32 = taxonomy-детекция неоднозначности по 6 типам (AmbiSQL)**

Проблема 1 — **фреймирование задачи в промпте:**
```
Было: "По умолчанию считай запрос ОДНОЗНАЧНЫМ. Неоднозначность — исключение"
```
→ LLM искал причины НЕ ставить флаг → 0/9 gold-ambiguous вопросов детектировалось

```
Стало: "Это задача сопоставления синтаксического паттерна, не философское суждение"
```
→ 21/24 gold-ambiguous вопросов детектировалось корректно

Проблема 2 — **JSON parse errors:**
- LLM добавлял текст после `}` или вставлял raw newlines внутри строк
- 8/24 вопросов падали с `JSONDecodeError` → FEAT_12 fallback → taxonomy игнорировалась

**Фикс:**
```python
# Было (сломано):
sanitized = re.sub(r"[\x00-\x08\x0b\x0c\x0e-\x1f]", "", text).replace("\n", "\\n")
# .replace("\n", "\\n") превращает структурные переводы строк между JSON-токенами
# в буквальные \n — невалидный JSON-токен

# Стало:
sanitized = re.sub(r"[\x00-\x1f]", " ", text)
# Пробел валиден в любом месте JSON — и внутри строк, и между токенами
```

## Slide 7 — Прогрессия гибридных экспериментов

| Эксперимент | Фичи | BIRD | AMB | Ключевое изменение |
|-------------|------|------|-----|-------------------|
| **Baseline** | — | 36.36% | 54.17% | Стартовая точка |
| **Hybrid 1** | FEAT_2+12+32+33+35 | 40.91% | 70.83% | Taxonomy prompt: философия → паттерны |
| **Hybrid 2** | +FEAT_3+4+8+17+18+19+27+29+30 | 50.00% | 66.67% | BIRD-фичи добавлены; JSON errors ещё не пофикшены |
| **Hybrid 3** | те же | 50.00% | **87.50%** | JSON парсер + counterexamples для FP/FN |
| **Hybrid 4** | те же | **54.55%** | **95.83%** | Alias check rule в SQL_PROMPT |
| **Hybrid 5** | те же | 54.55% | 91.67% | TO_DATE retry-rule (Q180 не починился) |

**Почему AMB упал с 70.83% → 66.67% при добавлении BIRD-фич (Hybrid 2)?**
JSON parse errors. FEAT_32 падала с `JSONDecodeError` на 8/24 вопросах → FEAT_12 fallback → taxonomy игнорировалась, и вопросы шли на SQL generation вместо `"ambiguous"`.

**Почему Hybrid 4 дал +4.55% BIRD (54.55% → +alias rule)?**
Два вопроса в BIRD-датасете проваливались из-за alias-ошибок:
- Q685: `"viewcount"` vs `"ViewCount"` (case sensitivity)
- Q17: alias `sc` использовался в SELECT, но не был объявлен в FROM

Добавление одного правила в SQL_PROMPT: _«каждый alias в SELECT/WHERE/ORDER BY ОБЯЗАН быть объявлен в FROM или JOIN»_ — устранило оба случая.

## Slide 8 — Ключевой архитектурный инсайт: два несовместимых режима

**FEAT_34 (auto-resolve) создаёт жёсткий потолок на AMB:**

```
AmbiSQL pipeline:
  Stage 1: _detect_ambiguity_by_taxonomy() → is_ambiguous?
  Stage 2a: _generate_clarification_question() → вопрос + варианты
  Stage 2b: _auto_resolve_ambiguity() → LLM выбирает вариант → переписывает запрос → SQL
```

При FEAT_34=True:
- **Любой** вопрос в итоге генерирует SQL (auto-resolve всегда "угадывает" ответ)
- `{"status": "ambiguous"}` **никогда не возвращается**
- AMB accuracy = % вопросов, где LLM угадал правильно ≤ 62.5%

| Режим | FEAT_34 | BIRD | AMB | Почему |
|-------|---------|------|-----|--------|
| **Detect-only** | ✗ | 54.55% | 91–96% | Taxonomy корректно возвращает `"ambiguous"` |
| **Auto-resolve** | ✓ | ~45% | ≤ 62.5% | Все вопросы → SQL, AMB metric заморожен |

**Вывод:** FEAT_34 полезна в продакшн-продукте (нет живого пользователя для уточнения), но **несовместима с бенчмарк-метрикой AMB**.

## Slide 12 — Итоги и выводы

### Что работает

1. **Статистика данных важнее структуры.** FEAT_2 (+9.09%) обгоняет FEAT_1 FK-связи (−9.09%). LLM эффективнее использует min/max/top-K, чем граф зависимостей.

2. **Не-аддитивность сигналов.** FEAT_2 (+9.09%) + FEAT_3 (+4.55%) + FEAT_4 (+4.55%) ≠ +18.19%. В комбинации они чинят частично те же 2–3 вопроса → реальный прирост ~12%.

3. **Фреймирование промпта критично.** FEAT_32 в isolation: −8% AMB → после переписывания как паттерн-матчинг: +37% AMB в hybrid. Та же фича, другое фреймирование.

4. **Инфраструктурные фичи — обязательный base-stack.** Без FEAT_18/19 — rate-limit cascade убивает прогон. Это не "опциональные улучшения".

5. **AMB и auto-resolve несовместимы.** FEAT_34 хороша в production (нет пользователя для уточнения), но блокирует метрику AMB на 62.5%. Выбор архитектуры зависит от use case.

### Финальные числа

```
Baseline → Оптимальная комбинация
BIRD:  36.36% → 54.55%  (+18.19pp, +50% относительно)
AMB:   54.17% → 91–96%  (+37–42pp, +69–78% относительно)
```
