# AdvText2SQL — описание проекта

## Аннотация

**AdvText2SQL** — исследование двух взаимодополняющих направлений автоматизации Text2SQL: (1) автономной специализации модели под конкретную базу данных без ручной разметки и (2) повышения качества генерации SQL и детекции неоднозначных запросов через промпт-инжиниринг и архитектурные практики.

Первое направление — пятистадийный пайплайн (Profile → Generate → Validate → Fine-tune → Serve), который по URL произвольной PostgreSQL-БД за ~30 минут строит специализированный Text2SQL-инструмент: профилирует схему и статистику данных, генерирует синтетические Q-SQL пары (шаблонами и через LLM), фильтрует их трёхуровневой валидацией и дообучает LoRA-адаптер на Qwen2.5-Coder-7B. Результат — 39.4% execution accuracy на BIRD card_games subset против 38.7% у классического full-FT на 10× большем размеченном вручную корпусе.

Второе направление — систематическое исследование того, какие промпт-инжиниринг практики и архитектурные решения реально влияют на качество SQL-генерации (бенчмарк BIRD) и на детекцию неоднозначности запросов (бенчмарк Ambrosia). Через ablation-тестирование 34 изолированных фич построена модель влияния: статистика данных оказалась важнее структуры схемы, а добавление FK/PK в промпт парадоксально снижает точность на 9 п.п. (LLM начинает строить лишние JOIN-ы). Реализован двухступенчатый модуль AmbiSQL для классификации и прояснения неоднозначных вопросов, поднявший точность детекции с 54% до 96% на малом датасете.

Оба направления используют общую evaluation-инфраструктуру (BIRD + Ambrosia, сравнение result-sets через execution accuracy) и взаимно дополняются: feature-флаги встроены в автономный пайплайн как опциональные параметры инференса, а планы по развитию предусматривают обучение классификатора, который будет динамически подбирать набор фич под конкретный запрос — направление, синергичное с автономной специализацией модели.

Прикладная мотивация — снижение порога входа в production-применение Text2SQL: вместо недель ручной разметки под каждую корпоративную БД и угадывания "правильного" промпта пользователь получает воспроизводимую методологию выбора и автоматической адаптации инструмента под целевую БД и характер запросов.

## Проблематика

Универсальные Text2SQL-модели, обученные на стандартных бенчмарках, в production сталкиваются с двумя системными проблемами. **Первая** — отсутствие специализации под конкретную БД: модель галлюцинирует имена колонок, выдумывает FK-связи и игнорирует domain-специфику (форматы дат, бизнес-правила, enum-значения), а классическое решение — ручное дообучение под каждую новую БД — требует недель экспертной работы и не масштабируется. **Вторая** — игнорирование неоднозначности: модель генерирует SQL даже для вопросов с несколькими валидными интерпретациями (например, «после войны» — точная дата или весь год?), что даёт разрыв точности до 2× по сравнению с системами, явно детектирующими и проясняющими неоднозначность.

## Постановка задачи

Дано: URL произвольной PostgreSQL-БД с правом READ-доступа и набор пользовательских NL-вопросов. Требуется решить две связанные задачи: (1) автоматически, без участия человека-разметчика, построить специализированный Text2SQL-инструмент с execution accuracy не ниже classical full-FT подхода; (2) систематически определить, какие промпт-инжиниринг и архитектурные практики повышают как точность SQL-генерации, так и качество детекции неоднозначных запросов, и в какой комбинации. Метрики: execution accuracy (сравнение result-sets gold/predicted SQL через set-equality) на BIRD и accuracy детекции неоднозначности на Ambrosia. Ограничения: модель должна влезать на A100 40GB (4-bit), обучение — укладываться в Colab, синтетика не должна содержать модифицирующих SQL-операций, PII не должны утекать к LLM-провайдерам.

## Описание технического решения

**Автономный пайплайн** (`profiler → synth → validate → training → serve`, ~5000 строк, 35 unit-тестов) извлекает метаданные и статистику БД (~120 запросов), генерирует Q-SQL пары двумя параллельными генераторами (25 SQL-шаблонов + LLM gpt-4.1/4o-mini/codex), фильтрует их трёхуровневым валидатором (sqlglot-парсинг → SELECT-whitelist → реальное исполнение), и обучает LoRA-адаптер (r=16, α=32, max_seq_length=12288) на Qwen2.5-Coder-7B-Instruct. Обученный адаптер разворачивается как vLLM-Docker + MCP-сервер с middleware для self-healing цикла.

**Feature engineering и AmbiSQL.** Через ablation v2 (leave-one-in: каждая из 33 фич тестируется изолированно против baseline) на обоих бенчмарках (BIRD large 241 вопрос, Ambrosia large 240 вопросов) построена честная модель вклада каждой практики. Выявлены нелинейные эффекты: FEAT_35 (TSV-формат) в изоляции снижает точность BIRD ниже baseline, тогда как в комбинации с FEAT_2 помогает; FEAT_14 (строгие SQL-правила) даёт наибольший одиночный прирост (+25 вопросов BIRD). По результатам ablation построены матрицы per-question feature attribution (241×33 для BIRD, 240×33 для Ambrosia) — основа для обучения multilabel-классификатора динамического выбора фич. Параллельно реализован AmbiSQL — двухступенчатый модуль детекции неоднозначности: taxonomy-классификатор (типы A1–A6) + генерация уточняющих вопросов, дополненный regex stop-filter для отсечения ложных срабатываний без лишних LLM-вызовов. Обе системы используют единую evaluation-инфраструктуру для сравнения метрик.

## Полученные результаты

| Направление | Метрика | Результат |
|---|---|---|
| Автономный пайплайн | BIRD card_games (gpt-4.1, RU+EN синтетика) | **39.4%** vs 38.7% classical full-FT (10× меньше данных) |
| Автономный пайплайн | Эффект evidence в инференсе | +12.9 п.п. без дообучения |
| Feature engineering | BIRD small (best combo) | 36.4% → **54.6%** (+18 п.п.) |
| Feature engineering | BIRD large (best combo) | 38.2% → **44.8%** (108/241, +6.6 п.п.) |
| Feature engineering | BIRD large (top-1 фича: FEAT_14) | 38.2% → **42.7%** (+4.5 п.п.) |
| AmbiSQL | Ambrosia small | 54.2% → **95.8%** (+42 п.п.) |
| AmbiSQL | Ambrosia large (top-1 фича: FEAT_13) | 55.9% → **62.1%** (+6.2 п.п.) |

Дополнительно установлены эмпирические закономерности: (1) языковой инвариант train↔inference — модель, обученная на русской синтетике, не переносится на английский тест, смешанный корпус снимает рассинхрон (+17 п.п.); (2) фреймирование промпта — архитектурное решение: одна и та же фича AmbiSQL даёт −8% или +37% к точности в зависимости от формулировки; (3) нелинейность фич — FEAT_35 (TSV) в изоляции снижает BIRD ниже baseline, но в комбинации с FEAT_2 помогает; сумма одиночных приростов (+83 вопроса) превышает прирост лучшей комбинации (+16 вопросов) из-за пересечений.

## Дальнейшие планы по развитию

1. Прогон автономного пайплайна на enterprise-БД (30+ таблиц, 500+ колонок) и проверка адаптивного масштабирования объёма синтетики.
2. DPO/RLAIF поверх SFT — оптимизация по execution-результату как сигналу награды.
3. Расширение на другие СУБД (MySQL, Snowflake, BigQuery).
4. Redact PII на стадии профилирования перед отправкой данных внешним LLM-провайдерам.
5. **Динамическая селекция feature-флагов** — матрицы per-question feature attribution построены (241×33 BIRD, 240×33 Ambrosia); следующий шаг — обучение multilabel-классификатора (sentence-transformer + Linear + Sigmoid, BCEWithLogitsLoss), который подбирает оптимальный набор фич под конкретный запрос вместо статической комбинации; далее — DB-aware scoring и AutoML поверх.
6. Self-healing production-цикл и интеграция MCP-сервера с BI-системами (Metabase, Superset).
