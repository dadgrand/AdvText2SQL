# AdvText2SQL · Выбор SQL по изменению результата

**Приоритет — опциональный эксперимент после завершения основного LoRA-трека и его финальной оценки.** Лид запускает пилот, если остаются время команды и вычислительный бюджет. Для первого прогона достаточно текущей 7B-модели, PostgreSQL и существующего харнесса. Обучение нового адаптера — отдельное решение по результатам пилота.

## Что хотим узнать

Может ли модель точнее выбрать правильный SQL, если ей задать узкий вопрос: «Как изменится ответ пользователя после добавления одной записи?» Сравниваем этот подход с прямым выбором по тексту SQL и с предсказанием полного ответа на мини-базе. Особый интерес представляет evidence: замечает ли модель, что смена определения бизнес-метрики меняет правильный ответ?

**Пример.** Вопрос: “How many distinct customers made a successful payment in March 2025 UTC?” У Анны уже есть успешная мартовская оплата, у Бориса оплат ещё нет. Каждая строка ниже — отдельное изменение одной и той же исходной базы.

| Добавленная запись | Верный эффект | Какую ошибку выявляет |
|---|---|---|
| Вторая успешная оплата Анны в марте | Без изменения | Подсчёт платежей вместо клиентов |
| Первая успешная оплата Бориса в марте | +1 | Пропущенный подходящий клиент |
| Неуспешная оплата Бориса в марте | Без изменения | Пропущенный фильтр статуса |
| Успешная оплата Бориса 1 апреля ровно в 00:00 UTC | Без изменения | Включённая верхняя граница периода |

Для отдельной проверки evidence используйте вопрос о числе мартовских заказов и один новый заказ: оплата 31 марта, оказание услуги 1 апреля. При определении месяца по дате оплаты ответ растёт на один, при определении по дате оказания услуги остаётся прежним. Обе версии вопроса и обе исходные таблицы должны быть одинаковыми; меняется только evidence.

## Как поставить пилот

1. **Зафиксировать выборку и бюджет.** Предлагаемый масштаб — 100–200 вопросов внутренней валидации на нескольких схемах. Начать со скалярных счётчиков и трёх типов ошибок из примера: повторы сущностей, статус, границы времени. Выбирать вопросы по этим признакам до просмотра ошибок greedy. Сохранить ID, схему, gold, версию модели, renderer, настройки генерации и лимит задержки. Закрытый PG-hard использовать только по ранее установленному финальному протоколу.
2. **Один раз получить кандидатов.** На вопрос сохранить greedy SQL и до трёх альтернатив текущей 7B. Оставлять варианты, различающиеся трактовкой вопроса. Переименование алиаса само по себе разнообразия не добавляет. Зафиксировать один банк кандидатов для всех методов.
3. **Сначала измерить потолок.** На скрытых проверочных состояниях посчитать greedy EX и oracle@4 — долю вопросов, где хотя бы один кандидат проходит все проверки. Разность — максимально возможный выигрыш выбора в данном банке. До просмотра чисел записать минимальный выигрыш, который оправдывает стоимость. Если даже oracle его не достигает, остановиться и зафиксировать ограничение генератора.
4. **Подготовить изменения данных.** Для каждого вопроса построить маленькое валидное состояние PostgreSQL и несколько допустимых вставок из фиксированной библиотеки. Использовать DDL, ограничения, вопрос и доступное в проде evidence. Исполнить кандидатов до и после каждой вставки. Выбрать до двух вставок, которые лучше всего разделяют кандидатов по фактическому эффекту. При выборе вставок gold SQL и его ответы недоступны. Скрытые состояния для финальной оценки готовит evaluator отдельно.
5. **Сравнить три способа выбора.** Использовать одну версию модели, один банк SQL и общий лимит вычислений на вопрос. Сохранить реальное число токенов, вызовов модели, SQL-исполнений и задержку. Для двух методов с мини-базами передавать одинаковые состояния и изменения.

| Метод | Что видит модель | Как выбирается SQL |
|---|---|---|
| Прямой выбор | Вопрос, evidence, схема, тексты кандидатов | Модель выбирает ID. Порядок кандидатов перемешан воспроизводимо |
| Полный ответ | Вопрос, evidence, схема, данные мини-базы до и после вставки | Модель предсказывает два скалярных ответа. Выбираем SQL с наибольшим числом точных совпадений |
| Изменение ответа | Вопрос, evidence, схема, исходные строки и вставка | Модель предсказывает класс эффекта. Выбираем SQL с наибольшим числом совпавших эффектов |

Для двух методов с мини-базами модель не видит ни SQL-кандидаты, ни результаты их исполнения. Варианты класса для счётчиков: `unchanged`, `plus_one`, `minus_one`, `other`, `insufficient_information`. Неопределённый ответ пропускает проверку. Если все проверки пропущены, ни один кандидат не совпал или лидеры делят первое место, оставить greedy. Правило зафиксировать до скоринга.

**Стартовый prompt для модели эффекта**

```text
You receive an analyst question, its evidence, the PostgreSQL schema, a complete
small database instance, and one proposed insertion. Predict the change in the
scalar count requested by the analyst after that insertion. All other rows stay
the same. Use the business definition in the evidence and the stated time zone.
Return exactly one label: unchanged, plus_one, minus_one, other, or
insufficient_information. Use insufficient_information when the public inputs
admit interpretations with different effects.
```

## Как принять решение

Основная метрика — доля вопросов, на которых выбранный SQL совпал с gold на **всех скрытых проверочных состояниях**. Gold доступен только оценщику. На вопрос сохранять результаты всех методов, даже при возврате к greedy. Это позволяет отдельно посчитать исправления, испорченные правильные ответы, долю вопросов, где метод изменил выбор, и чистый выигрыш. Сравнить методы попарно на одинаковых ID; сообщить числители, знаменатели, интервал разницы, срезы по схемам и p50/p95 задержки.

**Результат для лида:** одна таблица с greedy, oracle@4 и тремя методами, файл с решениями по каждому ID и минимум по одному примеру полезного и ошибочного переключения, если такие были. При малом запасе oracle улучшать разнообразие кандидатов. Если запас есть, а предсказание эффекта проигрывает прямому выбору, разобрать ошибки предсказания и качество фикстур. Если метод даёт практически значимый выигрыш при допустимой задержке, повторить на других схемах. Только после подтверждения стоит обучать компактный классификатор эффектов: его метки получаются исполнением проверенного gold до и после изменения на **учебных** схемах.

## Ближайшие работы

SQLDriller уже использует контрпримеры между кандидатами и исполнение на мини-базах. CHASE-SQL исследует выбор между несколькими SQL, TS-SQL — тестирование для исправления семантических ошибок. Предмет этого пилота — сравнение **типизированного локального изменения** с предсказанием полного результата при одинаковых кандидатах и данных.
